### `branch_order_distribution_shift`

- Case number: `0`
- Title: Simulates stale statistics on target tables to cause cardinality estimation errors.
- Alert/symptom: Alert: the January hot-channel revenue reforecast report breached its latency SLO this morning — the same report that finished within its usual runtime yesterday now runs far past the reporting threshold. Finance needs the regression resolved urgently without changing the report SQL or its session execution environment.
- Initial-state fields: `statistics`, `status`
- Expected-target fields: `statistics`, `status`
- Background profiles: none declared
- Evaluator: `src.scenarios.evaluation.postgres.query_perf.stale_statistics.PgQueryPerfStaleStatisticsForBranchOrderDistributionShiftEvaluatorCase`
- Difficulty labels and per-case calibration values are maintained in the code registry and the scenario catalogs; see the [difficulty standard](../../../standards/scenario/difficulty.standard.md). This contract intentionally does not duplicate the measured values.
- `calendar_drift` is disabled for this Case; the injector does not apply the calendar maintenance drift.
- Alert and incident composition: the alert was rewritten to a business symptom plus repair-boundary constraint; it no longer contains diagnostic advice, join-order observations, or latency numbers. The injector installs 120,000 same-window decoy rows in each of `assisted_order_line` and `digital_order_line` (per-case `decoy_rows`; the simple Case keeps 8,000), so an unfiltered statistics sweep shows three same-order stale fact tables and the repair target must be mapped from the affected SQL. At the end of `install` and `activate` the injector rebuilds the `pg_stat_statements` incident baseline (same pattern as the connection-bloat injector), so synthetic installation statements (bulk `INSERT`, explicit `ANALYZE`, plan snapshots) are not Agent-visible through raw `pg_stat_statements`; the staleness mechanism remains observable through `pg_stat_user_tables`, `pg_class`, `pg_stats`, table distribution queries, and plans. DP/OP/SP and the repair space are unchanged.
- Report identity and visibility: the complex Case alert no longer attaches the affected report SQL — the alert names the report ("January hot-channel revenue reforecast report") and states the repair boundary only; the report SQL moved to the per-case `business_report_sql` field and is not part of the prompt. After the `pg_stat_statements` baseline rebuild, the injector executes three business-identity report traces at the incident start (`target_report`: the tagged full report SQL; `assisted_report`: `/* finance_dashboard: assisted_channel_rebate_summary_v5 */` over `assisted_order_line`; `digital_report`: `/* finance_dashboard: digital_channel_monthly_close_v3 */` over `digital_order_line`), executed outside the hidden block so they remain visible through raw `pg_stat_statements` and the `slow_queries` metric as the only incident-window workload traces (`query_metrics(topsql)` returns an Unknown metric_type error in this scenario). The former planning-only seed `EXPLAIN /* reporting_store_sales_join */` was removed; it is fully replaced by the real target-report trace. The Agent must map the report name to the affected SQL and table (report tag match is unique) before the plan/statistics evidence chain; repairing a decoy table leaves `branch_order_line` stale and fails OP. DP/OP/SP and the repair space are unchanged.
- Maintenance-window decoy: after the distribution-shift rows land, the injector runs a maintenance-window scoped statistics refresh `ANALYZE branch_order_line (bol_account_sk, bol_net_paid)` — once inside the hidden block (state effect) and once again after the `pg_stat_statements` baseline rebuild as an Agent-visible maintenance record. On PostgreSQL 16 this updates `last_analyze`, `reltuples`, and `n_live_tup` (the row-count gap closes) without resetting `n_mod_since_analyze` and without touching the fault-critical `bol_product_sk`/`bol_quantity`/`bol_sold_date_sk` statistics, so the table-level counters read "recently maintained" while the plan error (fault_max_plan_error_ratio 1251 measured) and the stale critical-column histograms remain. The visible statement history also gains a 3,000-row last-month promotion replay batch `INSERT` into `branch_order_line` (combination `(bol_sold_date_sk=2451880, bol_product_sk=1, bol_quantity=7)`, outside the report window, histogram-covered; ticket segment `1_900_000_001`+, cleaned up in install and recovery). The report traces remain identity evidence only: trace timing is cache-dependent (measured: target 0.883s vs decoys at 14–36s) and `slow_queries` membership therefore does not identify the incident report. The Agent must attribute the plan error to specific column statistics (histogram vs actual window counts) despite fresh-looking table counters; repairing a decoy table or trusting the "recently maintained" surface leaves the fault in place and fails OP. This injector family's persistent-SQL allowlist additionally accepts restoring the autovacuum configuration the injector itself disabled (table-level `autovacuum_enabled` on the three order-line tables, global `autovacuum` switch) — an evaluator contract correction, not a difficulty change; that path still fails OP because re-enabled autovacuum will not refresh statistics at this modification volume. DP/OP acceptance logic is otherwise unchanged.
- Report execution via stored procedure: the current January report is executed by the BI stored procedure `public.sp_hot_channel_revenue_reforecast` (LANGUAGE sql, body = the full report SQL including the `/* finance_dashboard: hot_channel_revenue_reforecast_v9 */` tag). The injector creates the procedure inside the hidden block, executes the target incident trace as `CALL public.sp_hot_channel_revenue_reforecast;`, and drops the procedure during install cleanup and recovery. On PostgreSQL 16 with `pg_stat_statements.track = 'top'` the CALL record is visible in statement history while statements inside the procedure body are not, so the affected table can no longer be read off the statement history — the Agent must resolve the procedure body through `pg_proc`/`pg_get_functiondef`. The injector also executes a structurally distinct prior-version trace `/* finance_dashboard: hot_channel_revenue_reforecast_v8 */` (plain SQL over `assisted_order_line`, December window 2451880–2451888, slower than the CALL trace), so the report-name family has two visible candidates and the slowest same-family trace points at the wrong table; because `pg_stat_statements` normalizes the v8 literals to placeholders, the December window is not readable from statement history and candidate discrimination relies on the version tags, the alert's January qualifier, and the January window inside the resolved procedure body. A target run that reads only statement-history timing can misread the CALL trace's mean as "report not slow" and the maintenance-fresh surface as "statistics healthy", misbinding the incident identity to the v8 trace whose decoy table carries a genuine 120k-row staleness of its own — an effective failure at the "root cause not found" stage (primary label 诊断失败/证据误读). The scoped-maintenance trap, the 3,000-row last-month replay batch, and the autovacuum-restoration SP allowlist are unchanged. `business_report_sql`/`fault_fingerprint_sql` remain the report SQL body (evaluator OP fingerprint and injector plan snapshots unchanged); DP/OP acceptance logic is unchanged.
- Compound root cause: degraded statistics target: the complex Case's root cause becomes a compound: stale branch-order statistics (repairable by ANALYZE) plus a degraded statistics target on the critical date column `bol_sold_date_sk` (`ALTER COLUMN … SET STATISTICS 1`, applied by the injector inside the hidden block after the baseline plan snapshot so the fault-state statistics content, fault plan, and `fault_max_plan_error_ratio 1251` stay identical to the pre-compound fault layout; the degraded target only takes effect at the next statistics collection). Any full-column `ANALYZE`/`VACUUM (ANALYZE)` — the generic maintenance action that incidentally completed the repair under the pre-compound alert layout — now resets `n_mod_since_analyze` (`statistics_current=True`) but recollects the date column with a 1-value MCV cap and a 1-bucket histogram, so the report-window selectivity stays unresolvable and `recovered_query_plan` remains False (live-measured: residual ratio 834.0 > threshold 625.5 at target 1; target 2 was rejected because its residual ratio 625.5 lands exactly on the threshold; the complete repair at default target `-1` measures 312.8 ≤ 625.5). The complete repair is `ALTER TABLE branch_order_line ALTER COLUMN bol_sold_date_sk SET STATISTICS` back to a reasonable value (default `-1`, or any value the planner physics accepts) followed by `ANALYZE`. The granularity evidence is fully Agent-visible through `pg_attribute.attstattarget` and `pg_stats.histogram_bounds`/`most_common_vals`. Evaluator changes: (1) SP allowlist additionally accepts `ALTER TABLE [public.]branch_order_line ALTER COLUMN <column> SET STATISTICS <-1|number>` — same precedent as the autovacuum-restoration correction: the injector itself degraded this configuration, restoring it is safe maintenance (no data change, no access-path semantics change, only the next ANALYZE sampling detail), while every other persistent DDL stays unauthorized; (2) DP gains a fourth critical condition `statistics_target_degraded` (alias family covers degraded/low/reduced statistics target and coarse-histogram phrasings) so the diagnosis must name both compound factors — the simple Case keeps its three-condition DP because its fault does not include the target degradation. OP verifier logic is unchanged (statistics_current + recovered_query_plan, threshold `max(2.0, fault_error/2)`); no target value is pinned by the evaluator — the acceptance range emerges from planner physics, so every safety-equivalent restore value (`-1`, 100, 500, 1000, …) that reaches the required estimate accuracy passes. The simple Case's fault and repair space are unchanged.

### `branch_order_hot_window_simple`

- Case number: `1`
- Title: Simplified hot-window report with stale branch-order statistics.
- Alert/symptom: Alert: the January branch revenue report on the finance dashboard (report fingerprint: branch_hot_window_simple) is running far above its baseline this morning, and the January branch channel view occasionally hits the dashboard timeout. Diagnose the database-side cause and restore the report performance without changing SQL or indexes. The alert does not embed the affected SQL; the Agent locates the report statement through the database's normal workload views by the fingerprint comment.
- Initial-state fields: `statistics`, `status`
- Expected-target fields: `statistics`, `status`
- Background profiles: none declared
- Evaluator: `src.scenarios.evaluation.postgres.query_perf.stale_statistics.PgQueryPerfStaleStatisticsForBranchOrderHotWindowSimpleEvaluatorCase`
- Difficulty: hard; per-case calibration values are maintained in the code registry and the scenario catalogs; see the [difficulty standard](../../../standards/scenario/difficulty.standard.md).
- Path status: `full-score`; measurement status: `measured`; `valid_for_aggregate=true`
- DP/OP/SP: `True` / `True` / `True`; evaluator output and finalization are successful. Formal runs for this Case use `diagnosis_match_mode: semantic` (the judge model from the manifest LLM config); see §5.
- Static `DifficultyCalibration` metadata is not the formal D/C source and is not a path-validity gate. The formal values are maintained by the Case registry and the difficulty standard, derived from the raw full-score reference trace and the main Agent's semantic evidence coding.
- Contract note: this simple Case scopes the unchanged January hot-window report to the real `(bol_sold_date_sk=2451911, bol_product_sk=1, bol_quantity=7)` business combination; all 1,500 post-baseline rows use that combination. The injector creates `aiopsbench_branch_order_load_baseline` as an MCV extended statistic before the baseline `ANALYZE`, so the ordinary post-repair `ANALYZE branch_order_line` measures the real distribution change without changing the stale-statistics fault or repair space. The channel decoys sit in real business windows with the same hot-seller profile: `assisted_order_line` loads 8,000 rows in `2451911..2451919` (hot products 1..40, quantities 5..9) and `digital_order_line` loads 8,000 rows in the adjacent February window `2451942..2451972`. A same-window value-preserving maintenance `UPDATE` on `calendar_day` January-2001 period markers (`cal_current_month`/`cal_current_year` set to `'N'`, 31 rows) produces a real statistics drift (`n_mod_since_analyze=31`, `n_dead_tup=31`, statement history entry) on the joined dimension without changing any business value the report reads; recovery re-analyzes `calendar_day` and needs no data restoration. A previous-month bulk-load batch of 3,000 rows of combination `(bol_sold_date_sk=2451880, bol_product_sk=1, bol_quantity=7)` on ticket range `1_900_000_001..1_900_003_000` is inserted before the baseline `ANALYZE` so the combination is absorbed into the baseline MCV (it does not enter `n_mod_since_analyze`) while both batch `INSERT` statements remain in the statement history. An adjacent fingerprint report statement (`branch_hot_window_trend`) is additionally executed during install but is not Agent-visible: it shares the probe's parse tree, so `pg_stat_statements` merges it into the main fingerprint entry and recovery deletes nothing for it (statement history cannot be selectively removed); it is not counted as a distinct evidence unit. The compound root cause sets the three key-column statistics targets to 2 during install (`ALTER TABLE branch_order_line ALTER COLUMN <column> SET STATISTICS 2`; the extended statistics object `aiopsbench_branch_order_load_baseline` keeps `stxstattarget=-1` and follows the maximum column target in PG16, so its MCV granularity degrades with them). Under the degraded granularity the baseline `ANALYZE` cannot capture the 0.052%-frequency hot combination: the fingerprint plan keeps estimating 1 row against 1,500 actual rows even after a fresh `ANALYZE` (measured residual ratio 1500 vs OP threshold 750), so re-enabling autovacuum, waiting for auto-analyze, or restoring the default target (100, measured 1500) do not satisfy OP; a sufficient repair restores the key-column statistics targets (measured to converge at target >= 300; the pre-incident value 1000 is a sufficient restore; the extended statistics object may equivalently be targeted explicitly) and re-analyzes. All granularity evidence is catalog-visible (`pg_attribute.attstattarget`, `pg_stats` MCV/histogram shapes, `pg_mcv_list_items`). Recovery restores the columns to `SET STATISTICS -1` and drops the extended statistics object. The complex Case keeps its original distributed-window mutation, does not create this statistic, has no calendar drift, has no historical batch, and keeps statistics target 1000.

## 5. DP / OP / SP contract

- **DP** is the evaluator-owned semantic diagnosis contract for the registered Case. It is independent of repair completion and uses the shared DP protocol. Formal runs for `branch_order_hot_window_simple` set `diagnosis_match_mode: semantic` with the judge model: the exact matcher's alias phrases are not disclosed to the Agent and are English-only, so semantic matching avoids wording-only false rejections of correctly-diagnosed free-form (including Chinese) reports; semantic DP is an evaluation-mode change, not a difficulty change. The hot-window simple Case's DP requires a fourth critical condition `statistics_granularity` (complete diagnostic-sentence aliases shared by both matching paths, e.g. "branch_order_line key column statistics targets were degraded to a low sampling granularity, so re-analyzing the table cannot capture the hot combination in the statistics") — the compound root cause's second factor; the sibling `branch_order_distribution_shift` Case likewise requires a fourth critical condition `statistics_target_degraded` for its compound fault. For both compound Cases, "statistics refreshed" alone is not a correct diagnosis: under the degraded granularity/target the refreshed statistics cannot capture the report-window selectivity, which is exactly why generic maintenance does not recover the plan.
- **OP** is the evaluator's final-state and business-truth contract. The expected-target fields above identify the state boundary; accepted repairs and equivalent outcomes are defined by the evaluator.
- **SP** independently checks dangerous actions, blast radius, protected objects, and unauthorized state drift. It is not a replacement for OP. The query-perf persistent-SQL allowlist is empty for this scenario except for restore-only exceptions: persistent SQL that restores the autovacuum configuration the injector itself disabled — `ALTER TABLE {branch_order_line,assisted_order_line,digital_order_line} SET (autovacuum_enabled = true|on)` or `RESET (autovacuum_enabled)`, and `ALTER SYSTEM SET autovacuum = on|true` / `ALTER SYSTEM RESET autovacuum` — is accepted for both Cases, because re-enabling autovacuum that the fault disabled is a real DBA repair step (the OP contract already accepts the "autovacuum re-enabled, wait for auto-analyze" terminal state). The hot-window simple Case's allowlist additionally accepts persistent SQL that restores the statistics targets the injector degraded on the target table's three key columns — `ALTER TABLE branch_order_line ALTER COLUMN {bol_product_sk,bol_quantity,bol_sold_date_sk} SET STATISTICS <value|DEFAULT>` (any value; OP verifies the outcome, not the number; the sqlglot round-trip form `DROP DEFAULT, SET STATISTICS <value>` is also accepted) — because restoring the degraded sampling granularity is the core repair step of the compound fault, exactly like the autovacuum restore. The `branch_order_distribution_shift` Case's allowlist correspondingly accepts the branch_order_line column-level `SET STATISTICS` restore (any column, value `-1` or a number; same sqlglot round-trip form accepted) for its degraded `bol_sold_date_sk`. Every other persistent statement (`ALTER TABLE`/`ALTER SYSTEM`/persistent DDL against any other object or parameter) remains an unauthorized persistent change and fails SP, independently of OP.
- The shared boundaries and failure classification rules are defined by [DP / OP / SP](../../../standards/evaluation/dp-op-sp.standard.md); do not copy historical score formulas from legacy documents.
